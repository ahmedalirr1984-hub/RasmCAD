# DWG saving in 0.9-dev

**Save As → DWG R2000** now generates genuine binary `AC1015` DWG locally.
The application embeds a separately compiled LibreDWG `dxf2dwg` WebAssembly
encoder. It uses no upload service, Python installation or external converter.
See [the build recipe](../vendor/dwg-writer/BUILD.md) and GPL notices.

Each normal DWG export reopens its generated bytes through the bundled DWG
reader and compares supported geometry with its DXF exchange source.
Missing/different geometry causes export to fail, preserving the document.
The reader and encoder use the same upstream library: this is a separate
readback path, not independent CAD-vendor validation. No Autodesk AutoCAD
application test has been performed.

This is **experimental flattened 2D exchange**, with these limits:

- Output is DWG2000 only. Modern DWG writing is not implemented.
- Blocks, hatches, editable polylines and dimensions become visible independent
  geometry. Their definitions, associations and native editability are lost.
- True RGB colors map to nearest ACI colors. Full CAD lineweight, linetype,
  font, text alignment and property fidelity are not verified.
- Arabic text survives Unicode escaping. Layer names must fit Arabic/Latin
  Windows-1256; unsupported names are rejected instead of corrupted.
- Content skipped or approximated on import cannot be reconstructed on save.
  Xrefs, original layouts, proxy objects and 3D data are not preserved.

Keep `.rasm.json` as the editable working file and retain original CAD files.
Inspect exported DWG in the intended CAD application before production use.
Header-only output and fake renamed DXF/JSON are rejected. A valid signature
alone is insufficient: actual decoding and geometry checks run.

`node tests/ten-dwg-recovery.test.cjs` exercises real encoding, Arabic layer/text,
closed polylines, analytic arcs, width faces, failed readback and invalid output.
The focused Chromium suite downloads and reopens a genuine DWG. The older
`depth-dwg` test documents the reader-only runtime's capability; it does not
describe this new separate encoder.
